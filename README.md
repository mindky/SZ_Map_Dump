# SC Map Dump

Экспорт выбранных чанков игрового `map_cache` в Blender и Unreal Engine 5.

> **⚠️ Внимание.** Этот проект — форк инструмента дампа карты STALCRAFT,
> доработанный с помощью ИИ (правки реестров блоков, текстур, UE-экспорта и
> моделей растений). Часть решений принята без полной проверки против живого
> клиента. Формат 7.0 поддерживается, но на нём есть известные пробелы —
> см. «Известные ограничения» ниже. Используйте на свой страх и риск.

Поддерживаются:

- старый формат MDAT 5.0;
- формат MDAT 6.0 с terrain-данными и кешем объектов (object blob сохраняется и переносится вместе с чанком, но намеренно не резолвится в игровые меши);
- формат MDAT 7.0 (новый 16-байтовый заголовок региона и 8-байтовый ключ чанка внутри payload);
- оптимизированная блоковая геометрия, CTM-текстуры, маскируемые и невидимые блоки;
- 3D-модели растений/травы из `.mcsb`/`.mcsa` (через библиотеку `sc-file`) — вместо плоских крестов рисуется настоящая геометрия модели;
- выбор чанков и исключение отдельных world-каталогов через web-интерфейс;
- два режима экспорта: `.blend` для Blender и `.glb` + скрипт импорта для Unreal Engine 5;
- пакетный экспорт с автоматической склейкой GLB и синхронизацию реестров блоков.

Формат региона определяется автоматически для каждого `reg.*.mdat` по
содержимому, поэтому старые и новые карты можно обрабатывать одним и тем же
кодом без переключения настроек.

## Отличия формата 7.0

| | 5.0 / 6.0 | 7.0 |
|---|---|---|
| Запись заголовка региона | 24 байта: `sector, sectors, uuid0..uuid3` | 16 байт: `sector, sectors, key0, key1` |
| Размер заголовка | 24576 байт (6 секторов) | 16384 байта (4 сектора) |
| Начало payload | `declared_len, primary, add, raw_len, compressed_len` | `declared_len, key0, key1, primary, add, raw_len, compressed_len` |
| Секции блоков, tile-поток, zstd | без изменений | без изменений |

## Запуск

```powershell
pip install -r requirements.txt
python mdat_app.py
```

Откройте <http://127.0.0.1:39300/>, укажите папку игры, выберите чанки и запустите экспорт. Приложение автоматически выбирает самую новую числовую версию внутри `map_cache` (например, `7.0`).

Для текстур блоков используются файлы из `<game>\modassets\assets`, а локальные таблицы геометрии лежат в `assets/configs` репозитория.

Каждый экспорт создаёт отдельную папку в `exports/` с `job.json` и результатом выбранного режима:

- **Blender** (кнопка `Export .blend`) — `<name>.glb` и `<name>.blend`;
- **Unreal Engine** (кнопка `Export UE`) — `<name>.glb` (или `<name>_01.glb`, `<name>_02.glb`, ...), `map_meta.json`, `ue_import.py` и `UE_IMPORT.md`. `.blend` в этом режиме не создаётся, Blender не требуется.

## Экспорт в Blender

Кнопка `Export .blend` запускает обычный конвейер: пакеты экспортируются в GLB, склеиваются и открываются в Blender (5.1+) через `modules/glb_to_blend.py`, затем сохраняется `.blend`. Если результат не помещается в один GLB, `.blend` не создаётся — остаются только части `.glb`.

## Экспорт в Unreal Engine

Кнопка `Export UE` использует тот же GLB-конвейер, но дополнительно:

- не запускает Blender и не создаёт `.blend`;
- не запекает масштаб в вершины: GLB остаётся точным в блоках/метрах, а нужный масштаб применяется на этапе импорта. Цель задаётся полем `unreal scale` в интерфейсе (по умолчанию 100 UE-единиц на блок, то есть 1 м) или ключом `unreal_scale` в `/export`;
- сохраняет каждую часть в абсолютных мировых координатах блоков и даёт мешам уникальные имена, поэтому части не перезаписывают друг друга и не требуют ручной расстановки;
- генерирует в папке экспорта `map_meta.json` (части, имена мешей, их границы и целевой масштаб), `ue_import.py` (скрипт импорта под UE 5.x) и `UE_IMPORT.md` (краткая инструкция).

Импорт:

1. Включите плагин `glTF Importer`/`Interchange` (в UE 5.x обычно уже включён).
2. `Tools -> Execute Python Script...` -> выберите `ue_import.py` из папки экспорта (либо вставьте его содержимое в Output Log в режиме Python).
3. Скрипт импортирует все части в отдельную папку `/Game/MapDump/<имя экспорта>`, создаст материалы и текстуры и расставит статические меши в текущем уровне.
4. Масштаб подбирается автоматически: скрипт сравнивает реальные границы импортированных мешей с границами из `map_meta.json`. glTF хранит размеры в метрах, UE работает в сантиметрах, и разные версии Interchange конвертируют это по-разному, поэтому актёр получает масштаб, при котором один блок равен `unreal scale` UE-единиц.

Если карта всё равно выглядит в 100 раз больше или меньше, задайте `FORCED_ACTOR_SCALE` в `ue_import.py` (`100.0` или `1.0`) вместо автоопределения либо переэкспортируйте с другим `unreal scale`. Оси вручную настраивать не нужно: glTF-импортёр Unreal сам переводит Y-up в Z-up.

## Текстуры и прозрачность

- Полностью прозрачные DDS-записи в `blockMap.texarr` — это цветовые маски, а не видимые спрайты. `stalcraft:grass_side` и `stalcraft:dirt2_side` заменяются на `stalcraft:dirt`, а пустые overlay-иконки пропускаются, иначе в стенах появляются дырки.
- Режим альфы выбирается по реальному распределению пикселей: почти непрозрачные спрайты (шум DXT у камня, земли, травы) остаются `OPAQUE`, cutout-растительность с плотными краями получает `MASK`, а вода, стекло и туман — `BLEND`. Из-за этого листва больше не просвечивает сама через себя, а вода остаётся полупрозрачной.
- Технические невидимые блоки (`stalcraft:b1`, `stalcraft:inv`, `stalcraft:dark` и подобные) по-прежнему не рисуются: их грани отбрасываются при `--hide-invisible`.

## Модели растений

Блоки-растения с конфигом `model`+`simple_render` (трава, цветы, крапива, камыш и т. д.) экспортируются как **настоящие 3D-меши** из `.mcsb`/`.mcsa`, а не плоские кресты. Для этого используется библиотека [`sc-file`](https://github.com/onejeuu/sc-file) (ставится вместе с `requirements.txt`).

Если `sc-file` не установлен или модель не найдена на диске, блок аккуратно откатывается к прежнему кресту — экспорт не падает.

## Пакетный экспорт

Вся карта (64 807 чанков, ~1.3 млрд блоков) не помещается в RAM одним куском: при загрузке мира в словари уходит примерно 275 байт на блок, то есть сотни гигабайт. Поэтому экспорт автоматически режется на пространственно компактные пакеты (Z-порядок), по умолчанию 500 чанков на пакет. Размер задаётся полем `chunks per batch` в интерфейсе или ключом `batch_chunks` в `/export`. Ограничение одинаково работает для обоих режимов.

Каждый пакет экспортируется отдельным процессом, и память освобождается до следующего пакета. Затем пакеты склеиваются модулем `modules/glb_merge.py`:

- если всё помещается в один GLB (жёсткий лимит контейнера — 4 GiB), получается один `.glb` и один `.blend` (в режиме Blender);
- иначе части объединяются в минимальное число `.glb`-файлов, каждый меньше 4 GiB (`name_01.glb`, `name_02.glb`, ...), а `.blend` не создаётся: одна сцена со всей картой не помещается в RAM. В режиме Unreal `ue_import.py` читает список всех частей из `map_meta.json` и импортирует их подряд.

В пакетном режиме (и в режиме Unreal) координаты остаются абсолютными мировыми координатами блоков, поэтому после склейки части не накладываются друг на друга. Склейка потоковая — двоичный буфер копируется с диска по частям, поэтому сам merge не требует памяти под весь результат. Текстуры и материалы при склейке дедуплицируются. Прогресс и итоговые файлы видны в `job.json` (`mode`, `batches`, `parts`, `parts_bytes`).

Замеры на реальной карте 7.0: 826 чанков (15,9 млн блоков) — 400 МБ GLB за 312 с; 350 чанков двумя пакетами по 175 — 300 МБ GLB за 180 с (включая склейку и импорт в Blender). Вся карта — это 1,27 млрд блоков, то есть примерно 50–60 ГБ готовых GLB и 8–10 часов работы. Столько же свободного места нужно на диске: временные пакеты удаляются сразу после склейки, но запас в один пакет (~4 ГБ) желателен.

Для всей карты один `.blend` получить нельзя: 700+ млн полигонов не помещаются в RAM. Части `.glb` открываются в Blender по отдельности (в Unreal — импортируются скриптом по очереди).

## Блоки и реестры

Геометрия и текстуры блоков берутся из трёх источников:

- `docs/block_registry.json` — соответствие `block_id -> type_id` (класс блока в игровых данных);
- `docs/external_config_block_registry.json` — внешние конфиги (иконка, `model`/`simple_render`, AABB, прозрачность). Внешний конфиг имеет приоритет над `block_registry`;
- `assets/configs/assets/pda/map_blocks.json` — PDA/миникарта (id/meta -> иконка и цвет), используется как резерв для иконок и как источник типов (`GRASS`, `WATER`, `LEAVES`, ...).

`docs/north_mines_geometry_by_block_id.json` — отчёт о геометрии по id, из него подхватываются стратегии рендера (`external_config_block`, `probuilder_*`, `smt_*` и т. д.).

Блок, которого нет ни в одном реестре, попадает в строку `unknown_ids=` лога экспорта и рендерится заглушкой. Чтобы этого не было, есть `tools/sync_block_registry.py`:

```powershell
python tools/sync_block_registry.py --dry-run        # только показать, чего не хватает
python tools/sync_block_registry.py                  # просканировать map_cache и дописать записи
python tools/sync_block_registry.py --from-tables    # без скана: объединить PDA-таблицу и geometry report
python tools/sync_block_registry.py --ids-json ids.json  # использовать готовый скан
```

Инструмент читает реальные чанки (или готовый JSON со списком `ids`/`id_meta`), сравнивает с реестрами и добавляет недостающие id в `docs/external_config_block_registry.json`. Запись выбирается по данным PDA-таблицы:

- растения и трава (`GRASS`, `PLANT`, `FLOWER`) — крест (`model` + `simple_render`), без коллизии;
- вода и листья — куб с прозрачностью;
- прочее — обычный куб;
- id, которого нет в PDA-таблице (новые декоративные растения вроде `4006`), получает крест с `customitems:tallgrass`.

Отчёт о том, что было добавлено (id, количество вхождений, топ `meta`, источник иконки), пишется в `docs/block_id_report.json`. История добавлений копится в поле `history`, так что после полной синхронизации там остаётся след последних правок.

Текущее состояние реестров: 244 внешних конфига и 156 записей `block_registry`, включая добавленные `4006` (крест-растение) и `4095` (вода). Экспорт `reg.-8.1.mdat` после этого проходит без `unknown_ids`.

## Известные ограничения

### Формат 7.0

- **Строения рисуются сплошными кубами.** Стены, трубы, полы, лестницы и мебель — это ProBuilder-блоки (`probuilder_shape_table`, `probuilder_carpenter_tile`, `probuilder_dynamic_bounds`, `type_custom_shape`). Их настоящая форма (тонкая стена, труба, плита пола) задаётся shape-таблицами из Java-классов игры, которых в репозитории нет — в логе экспорта `shape_tables=0`. Без таблиц каждый такой блок рендерится как куб 1×1×1, из-за чего строения выглядят «раздутыми» и «не в том масштабе».
- **Размещённые объекты (вертолёты, крупный декор) не экспортируются.** В mdat 7.0 нет object-блоба: после секций блоков и ProBuilder-тайлов чанк заканчивается. Если объект в игре стримится сервером, его нет в клиентском `map_cache`, и вытащить его оттуда невозможно ничем.

### Почему это не исправлено

Shape-таблицы лежат в `classes.jar` (62061 файл с md5-именами), зашифрованном AES-подобным шифром. Расшифровка происходит внутри кастомной JVM (`exbojdk` 9.0.6.4, `win64/java/bin/server/jvm.dll`, 33 МБ, обфусцирована). Агенты JVM выпилены на этапе компиляции: `-javaagent` отвечает `Instrumentation agents are not supported in this VM`, `-agentlib:jdwp` — `Debugging agents are not supported in this VM`. Поэтому дамп классов на лету невозможен, а статический реверс `jvm.dll` — отдельная большая задача без гарантии. Публичного дампа декомпиленных классов не найдено.

### Что работает

- рельеф и обычные блоки — полностью;
- растения, трава, цветы — настоящие 3D-модели `.mcsb`/`.mcsa` через [`sc-file`](https://github.com/onejeuu/sc-file);
- текстуры и прозрачность — починены (пустые маски, альфа-классификация);
- формат 6.0 с кешем объектов: object blob переносится вместе с чанком, но в игровые меши намеренно не резолвится.
